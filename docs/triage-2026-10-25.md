- ID 기억하기는 자동 로그인과 독립적으로 이메일만 localStorage에 저장한다. 체크 해제 시 삭제한다. 저장소 차단도 로그인을 막지 않는다.

## 위시리스트: 조사만 수행

실제 연결은 `/home` 서버 페이지 → `ChildHomeScreenClient` → `ChildScreen` → `MarketTab` → `MarketWishlistBottomSheet`다.

- `src/app/(child)/home/page.tsx`: 홈 조회 묶음에 `market_wishlist_items.select('store_item_id, quantity')`가 항상 포함된다. 마켓을 열지 않아도 조회한다. 운영 DB에는 `quantity`가 없어 10:06 KST에 `42703`이 기록됐다. 실패하면 빈 배열을 전달해 홈은 계속 표시된다.
- `MarketTab.tsx`: 초기 목록을 상태에 복사하고, 목록이 있을 때만 장바구니 버튼을 표시한다. 홈이 빈 배열을 주므로 현재 누락된 컬럼 상태에서는 기존 목록도 가려진다.
- `addWishlistOne`은 정의만 있고 호출/전달 지점이 없다. 현재 구매 확인창은 `submitPurchaseRequest` → `/api/market/request`로 직접 요청한다. 일반 구매에는 위시리스트 테이블이 필요하지 않다.
- 삭제/수량 변경 함수와 바텀시트 연결은 남아 있다. API의 GET은 구형 스키마에서 수량 1로 대체하지만 홈의 직접 조회에는 이 대체 처리가 없다.
- POST `set_quantity`는 컬럼 누락 시 `degraded: true` 성공을 반환한다. 화면은 현재 세션 수량이라는 안내를 띄우지만 DB에는 저장되지 않는다. 홈 재조회 시에는 목록 전체가 사라질 수 있다.
- `/api/market/wishlist`의 신규 삽입은 `ADD_TO_CART` 게임 이벤트에도 연결된다. 구형 스키마 대체 삽입 경로는 그 이벤트 전에 반환한다.

미운영 상태라면 추후 제거 후보는 홈 조회/props, MarketTab의 장바구니 상태·핸들러·버튼·시트다. 외부 API 소비 여부를 확인한 뒤 API도 제거할 수 있다. 구매 요청/승인/배송과 콘텐츠 티켓의 별도 수량 기능은 유지해야 한다. DB 테이블과 기존 기록 삭제는 필요 없다. 이번 작업에서는 위시리스트 코드와 DB를 변경하지 않았다.

## 게임 이벤트 중복 로그: 개선 계획만 작성

운영 로그의 `child_trigger_fired` 중복 키 오류 `23505`는 21건이다. SQL 모양만으로 각 건의 trigger_key를 구분할 수는 없다. 현재 코드에는 다음 두 경로가 있다.

1. `fireGameTrigger`: 미션 완료(FIRST_MISSION), 저금(FIRST_SAVE), 구매(FIRST_PURCHASE), 위시리스트 신규 삽입(ADD_TO_CART)이 매번 일반 INSERT를 시도한다. PK `(child_id, trigger_key)`가 중복을 막고 앱은 23505를 무시하지만 DB 로그에는 ERROR가 남는다.
2. 일일 칭찬 스티커: 미션 완료 API에서 날짜별 키로 동일한 INSERT를 실행한다. 지급 기준 달성 이후 추가 미션에서도 중복 오류가 발생할 수 있다.

현재 `TRIGGER_TO_ITEM` 매핑은 전부 null이라 첫 번째 경로는 아이템을 해제하지 않고 발동 이력만 기록한다. 그러나 같은 테이블은 실제 일일 스티커 중복 방지에도 쓰이므로 테이블이나 전체 호출을 일괄 삭제하면 안 된다.

개선 순서:

1. 두 INSERT를 `upsert(..., { onConflict: 'child_id,trigger_key', ignoreDuplicates: true }).select('child_id')`로 전환한다. 이는 중복을 에러로 만들지 않고 원자적으로 무시한다. 사전 SELECT 후 INSERT 방식은 동시 요청 경합을 해결하지 못한다.
2. 반환된 새 행이 있을 때만 지급한다. 기존 빈 배열 검사와 실제 장애 로그는 유지한다. 동일 키의 최초/재호출/동시 요청, 날짜가 바뀐 스티커 지급을 검증한다.
3. 별도 후속으로 발동 이력 기록과 실제 지급을 하나의 DB 트랜잭션으로 묶는다. 현재 지급 실패 시 이력만 남아 재시도가 막힐 수 있다. 아이템 매핑 재활성화 전과 일일 스티커 지급 안정화에 필요하다.

이번에는 게임 이벤트 코드를 수정하지 않았다. 최초 21건 전부가 어느 이벤트였는지와 과거 보상 손실량은 현재 로그만으로 확정하지 않았다.

## 후속 요청: 중복 로그 수정 및 실제 구매 검증

- 게임 발동 이력과 일일 스티커 게이트 INSERT를 `onConflict: child_id,trigger_key`, `ignoreDuplicates: true`인 upsert로 변경했다. 기존 행은 오류 없이 무시하고 새로 삽입된 행이 있는 경우만 지급을 계속한다. 실제 DB 오류 로그는 유지했다.
- `tests/market-live-check.mjs`를 명시적으로 실행해 로컬 프로덕션 서버와 운영 Supabase에 임시 자녀 계정을 만들고 실제 로그인·구매 API를 호출했다. 기존 사용자 데이터는 변경하지 않았다.
- 콘텐츠 2개 구매: HTTP 201, 수량 2·합계 가격·잔액 차감 확인. 같은 상품 재요청: 409, 추가 차감 없음. 다른 간식 구매: 201 및 정확한 잔액 확인. 잔액 0에서 다른 상품 요청: 400/insufficient_credits, 추가 구매 내역 없음. 총 구매 요청은 정상 2건만 생성됐다.
- 실제 두 번의 구매 후 FIRST_PURCHASE 이력 1건 확인. FIRST_SAVE 5개 동시 호출에서 1회만 신규 발동, 재호출은 건너뛰기 확인. 날짜별 스티커 게이트도 각 날짜마다 동시 3건 중 1건만 생성됨을 확인했다.
- 테스트 종료 시 Auth 계정을 삭제하고 profiles·child_stats·purchase_requests·child_trigger_fired에 남은 테스트 행이 없음을 확인했다.
- 전체 빌드·TypeScript 검사 및 인증 회귀 테스트 4개 통과. 구매 재현 범위는 실제 API 로그인·구매 요청·차감까지이며, 부모 승인·배송·실기기 UI 조작은 이번 검증에 포함하지 않았다.
- 중복 무시 동작 참고: https://supabase.com/docs/reference/javascript/upsert
