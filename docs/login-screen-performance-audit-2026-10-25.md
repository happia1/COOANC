# 로그인부터 첫 화면까지의 지연 분석 — 2026-10-25

사용자가 설명한 자녀 바로가기·즉시 보상·저금통→구매 계산 순서를 반영한 실행 계획은 [자녀 진입·계산 개선안](child-entry-and-balance-improvement-plan-2026-10-25.md)에 정리했다. 아래의 ‘미션 생성’은 설정이 아니라 날짜별 실행 기록 준비를 뜻한다.

## 범위와 측정의 한계

로컬 소스 `ee9ab5b`, 현재 프로덕션 빌드 산출물, 공개 배포 URL의 비로그인 응답, 운영 Supabase 로그/SQL 누적 통계/성능 Advisor를 분석했다. 앱 동작과 DB 설정/데이터를 수정하지 않았다. 관련 보상 분석은 `reward-processing-audit-2026-10-25.md`에 있다.

- Supabase 로그 구간: 2026-10-25 10:00~11:10 KST(01:00~02:10 UTC). 이후 실행한 임시 구매 계정 테스트 구간과 분리했다.
- 이 구간의 요청 전체를 집계한 것이며 특정 로그인 한 번을 끝까지 묶은 분산 추적은 아니다. DB 조회에는 화면 읽기 외 작업도 섞일 수 있다. p95는 관측 요청의 95%가 그 값 이내였다는 뜻이다.
- 공개 URL 측정은 현재 접속 환경에서 각각 3회, 비로그인 상태의 TTFB(첫 응답까지)를 잰 값이다. 비밀번호 검증·인증된 홈 렌더·모바일 화면 완성 시간을 대신하지 않는다.
- 프로덕션 배포가 정확히 어느 Git 커밋인지, 사용 기기의 LCP/JS 실행 시간, 과거 CPU·메모리·연결 포화는 확인하지 못했다.

## 원인 1: 인증 이후 단계가 길고 인증 확인이 반복됨 — 높은 확신

부모 계정에 자녀 한 명이 연결된 수동 로그인 경로는 다음과 같다.

```text
/login
  → POST /api/auth/sign-in (비밀번호 검증·쿠키)
  → GET /api/auth/post-login-redirect (getUser → family_links)
  → GET /api/parent/enter-child-ui (getUser → 부모 프로필 → 가족 연결 확인 → 미리보기 쿠키)
  → /home middleware (getUser)
  → 자녀 context/layout (getUser → 프로필 → 부모라면 가족 연결)
  → 홈 데이터 조회 → JS 준비 → 화면 완성
```

정상 경로에서도 비밀번호 검증 뒤 getUser가 코드상 4회 존재한다. 자녀 계정의 직접 홈 진입과 부모 홈 진입은 post-login API·middleware·페이지 인증에 각각 존재한다. 동일 요청 내 React cache는 layout/page 중복을 줄이지만, 별도 HTTP 요청인 post-login/enter-child-ui/middleware 사이의 왕복까지 없애지 않는다.

`getCachedParentAuth`도 getUser → profiles → family_links를 차례대로 기다린 뒤 부모 홈 데이터 조회를 시작한다. 캐시라는 이름과 달리 React cache는 일반적인 장기 데이터 캐시가 아니다.

개선 후보: 비밀번호 로그인으로 이미 검증한 사용자에 대해 같은 서버 처리에서 목적지·연결 자녀를 결정하고 필요한 미리보기 쿠키까지 설정하면 중간 왕복을 줄일 수 있다. 자동 로그인도 검증·목적지·쿠키 처리를 묶는 방향이 적합하다. 권한 확인을 생략하거나 사용자별 인증 응답을 공용 캐시하는 방식은 사용할 수 없다.

## 원인 2: 첫 화면이 열리지 않은 패널의 DB 조회까지 기다림 — 높은 확신

`src/app/(child)/home/page.tsx:146`은 14개 비동기 작업을 Promise.all로 묶는다. 일부는 요청 내 캐시로 재사용되므로 14개가 항상 14 SQL 실행을 뜻하지는 않는다. 그러나 다음 데이터가 모두 끝나야 홈 컴포넌트를 반환한다.

- 핵심: 스탯·프로필/나이·가족·미션 템플릿·당일 미션·당일 루틴.
- 패널: 스티커 지급/배치, 꾸미기 해금, 숨긴 마켓 상품, 상품 가격 덮어쓰기, 전체 활성 상품, 최근 구매 내역.

병렬 조회여도 가장 느린 요청을 기다린다. 현재 마켓·스티커 UI는 사용 시 동적 import하지만 **데이터 조회는 여전히 첫 화면에 포함**돼 있다. 위시리스트 조회는 앞선 수정에서 제거돼 현재 원인이 아니다.

레벨 8 이상이면 1차 묶음이 전부 끝난 다음 콘텐츠 채널·카테고리·이용권·세션·가족·숨김의 6개 조회를 추가로 기다린다. family_links도 이 헬퍼에서 별도로 다시 읽는다. 콘텐츠 패널을 열지 않아도 홈 반환이 지연된다.

개선 후보: 실제 첫 화면에 필요한 표시를 기준으로 패널 조회를 분리하고, 필요한 경우 패널을 열기 전 한가할 때 미리 읽는다. 단순 분리만 하면 패널 열기 지연으로 옮겨갈 수 있으므로 홈 준비 시간과 패널 준비 시간을 따로 측정한다.

## 원인 3: 화면 조회에 당일 미션 생성/복구가 섞임 — 조건부, 높은 확신

홈은 템플릿 전체를 읽어 오늘의 풀을 계산하고 누락분을 찾는다. 누락 시 배치 upsert → 전체 미션 재조회를 기다린다. 배치 실패 시 행별 병렬 INSERT까지 추가한다. 클라이언트도 빈 목록이면 `/api/mission/child-today`로 한 번 자동 복구한다.

자정 직후·루틴 변경 직후·당일 첫 접속의 지연이 더 커질 수 있다. 매 접속마다 삽입한다는 뜻은 아니다. 이는 예전에 “스페셜만 있고 일상 카드가 없음”을 고치려 추가된 동작이므로 속도만을 이유로 제거하면 안 된다.

개선 후보: 정상 접속의 읽기와 필요한 생성/복구 경로를 구분하고, 날짜·자녀·루틴 기준의 안전한 보충 생성을 한 번에 처리한다. P1 완료·지급 트랜잭션 수정과 데이터 권한 설계도 맞춰야 한다.

## 원인 4: 오류 방어용 재시도와 대기 화면이 지연을 증폭 — 높은 확신

- middleware fetch는 3.5초 제한, 서버 조회는 12초 제한이다. getUserForNavigation은 일시 오류 응답에 한 번 추가 시도한다.
- 프로필/가족 헬퍼와 fetch 래퍼, 미션 템플릿 호출부에도 재시도 계층이 있다. 어떤 오류인지에 따라 적용 경로가 달라 상한을 단순 곱할 수는 없지만 같은 실패가 여러 층에서 다시 시도될 수 있다.
- `/login`은 자동 로그인 설정을 읽고 확인 요청이 끝나기 전까지 입력 폼을 숨긴다. 4초 후에는 안내 문구만 바뀌고 30초 후 폼을 연다. 정상 응답에도 30초를 기다리는 코드는 아니다.
- P2 수정의 인증 직렬화는 쿠키 충돌을 막는 장치다. 처리 중인 요청이 늦으면 다음 인증도 기다린다. 이를 제거하기보다 실제 중복 요청과 서버 지연을 줄여야 한다.

개선 후보: 하나의 진입에 총 대기 예산을 두고, 전송 실패/재시도 가능한 서버 오류/권한 오류/필수 데이터 누락을 구분한다. 과거 기본 캐릭터·빈 미션 화면이 사용자에게 데이터 삭제처럼 보였던 이력이 있으므로 오류를 빈 데이터로 대체하지 않는다.

## 원인 5: DB 정책·지역·JS·에셋 — 추가 확인이 필요한 보조 원인

- Performance Advisor: auth_rls_initplan 98건, multiple_permissive_policies 114건, unindexed_foreign_keys 23건. 점검 후보이며 개수만으로 이번 지연의 원인이라고 할 수 없다. 대상 쿼리의 EXPLAIN과 표본별 응답을 확인한 뒤 바꿔야 한다. [RLS 성능 경고 설명](https://supabase.com/docs/guides/database/database-linter?lint=0003_auth_rls_initplan).
- 홈 페이지에는 Tokyo `hnd1`, DB는 Seoul 지역이다. 인증·진입 API에는 preferredRegion 선언이 없어 실제 Vercel 프로젝트 기본 리전을 별도로 확인해야 한다. 현재 정보로 API가 미국에서 실행된다고 단정할 수 없다.
- ChildScreen은 동적 청크 준비 후 실제 화면이 나타난다. 해당 기능 코드가 포함된 빌드 청크 하나는 raw 약 162KiB/gzip 약 47KiB였으나 의존성을 포함한 전체 전송량·폰의 JS 처리 시간은 별도다. 전체 .next 디렉터리 크기를 첫 화면 다운로드 크기로 해석하지 않았다.
- 홈 배경 PNG는 약 223KiB다. 큰 이미지가 전혀 없다는 뜻은 아니지만, 확인된 반복 인증·연속 DB 조회보다 먼저 주원인으로 지목할 근거는 부족하다.
- 다이어리 배경은 홈 마운트 시 probe하며 파일이 없으면 404가 난다. 비동기라 홈 서버 반환을 직접 막지는 않지만 개발 모드에서는 부가 컴파일/요청을 만들 수 있다.
- 개발 모드의 수십 초 첫 컴파일 기록은 프로덕션 처리 시간과 분리한다. production build의 응답과 실제 기기 네트워크 타임라인으로 다시 비교해야 한다.
- 공휴일 동기화는 로그인 화면에서는 건너뛰고 백그라운드로 실행한다. 부모 AI 최초 실행도 `void fetch`라 홈 서버가 결과를 await하지 않는다. 둘을 로그인 대기의 직접 원인으로 보지는 않는다.

## P1과 함께 진행할 순서

1. 인증 확인/목적지/미리보기 쿠키의 중복 왕복을 줄이고, 로그인과 홈의 단계별 시간을 남긴다. JWT 검증 방식 변경은 키 종류·세션 취소 요구를 확인한 뒤 결정한다. [Supabase 인증 함수 선택](https://supabase.com/docs/guides/auth/server-side/creating-a-client).
2. 홈 핵심 데이터와 마켓·스티커·콘텐츠 준비를 나눈다. 자녀·가족별 접근 검증과 최신 잔액은 유지한다.
3. P1의 완료/취소/재완료 트랜잭션 및 권한을 정리하면서, 홈의 미션 생성/복구에 같은 데이터 규칙을 적용한다. 기존 템플릿 캐시가 삭제된 미션 ID로 백필을 실패시킨 이력이 있어 임의 TTL 캐시를 다시 붙이지 않는다.
4. 확인된 느린 조회에 한해 RLS·인덱스·조회 범위와 API 지역을 조정한다. 그 후 기기별 JS/이미지 병목을 측정한다.

성과 기준은 `비밀번호 제출→클릭 가능한 첫 화면`, `자동 로그인 접속→클릭 가능한 첫 화면`, `부모→자녀 전환`, `마켓 열기`를 각각 p50/p95로 기록하는 것이다. 현재 공개 URL TTFB·Supabase 처리 시간·누적 SQL 평균만으로 이 네 시간을 정확히 산출하지 않는다.
