# 자녀 앱 진입·반응·계산 순서 개선안 — 2026-10-25

2026-10-26 구현 및 운영 적용 현황은 [개선 작업 반영 현황](improvement-implementation-2026-10-26.md)을 따른다. 아래 내용은 수정 전 분석/계획이다.


사용자가 설명한 실제 사용 흐름에 따라 기존 성능 분석을 보완한다. 이 문서는 계획이며 앱 코드나 운영 DB를 변경하지 않는다. 보상 P1도 분석·수정안 단계로 유지한다.

관련 문서: [접속 지연 분석](login-screen-performance-audit-2026-10-25.md), [보상 이력·P1 분석](reward-processing-audit-2026-10-25.md).

2026-10-26 사용자 확정: 자정 예약 실행의 대상은 자녀 앱의 날짜별 미션 카드 준비뿐이다. 다른 아이콘의 데이터는 해당 아이콘을 실행할 때 조회하며, 자정 일괄 조회·갱신 대상에 넣지 않는다. 홈에 직접 표시되는 저장 잔액·저금통·화분 상태는 홈 진입 시 읽는다.

## 반드시 유지할 동작

- 부모의 평소 진입도 설정된 자녀 화면으로 바로 연결한다. 부모 요청 확인 화면으로 향하는 알림·명시적 이동은 별도로 유지한다. 여러 자녀의 선택 및 미리보기 권한 확인도 보존한다.
- 첫 화면에는 오늘의 설정된 미션, 이전에 저장된 크레딧·저금통·하트·화분 상태가 정확히 표시되어야 한다. 조회 실패를 0원·빈 미션·초기 화분으로 표현하지 않는다.
- 미션을 누른 즉시 카드 반응과 보상 효과가 나타나야 한다. 표시 효과가 빠른 것과 그 보상을 다음 거래에서 사용할 수 있는 것은 구분한다.
- 미션 보상 → 저금통 이동 → 구매처럼 서로 금액에 영향을 주는 작업은 앞의 저장 결과가 확정된 후 다음 계산을 실행한다. 처리 중 안내는 유지하되 서버 저장이 끝난 뒤에도 고정 시간을 추가로 기다리게 하지 않는다.
- 마켓·스티커·콘텐츠의 전체 목록은 해당 아이콘을 눌렀을 때 읽는다. 첫 화면에 실제 표시되는 최소 상태는 예외다.

## 1. 자녀 첫 화면에 필요한 조회만 남긴다

| 첫 화면에서 기다릴 것 | 해당 기능을 열 때 조회할 것 |
|---|---|
| 검증된 로그인·자녀 연결·접근 권한 | 마켓 전체 상품·개별 가격·숨김 설정·구매 내역 |
| 프로필과 오늘 날짜·루틴에 맞는 미션/보상 설정 | 스티커 전체 지급·배치·보관함 데이터 |
| 저장된 크레딧·저금통·하트·화분, 화면상 필요한 보너스 상태 | 콘텐츠 채널·분류·전체 이용권 등 패널 목록 |
| 홈에서 실제 보이는 알림 개수나 진행 중 사용 제한에 필요한 최소 상태 | 그 밖의 닫힌 패널 상세 데이터 |

사용 중인 콘텐츠 세션의 제한이나 홈에 표시되는 스티커 알림까지 무조건 미루면 안 된다. 실제 첫 화면 사용처를 확인해 최소 상태만 남긴다. 구매 확정 시에는 서버의 최신 잔액·가격·권한을 다시 적용한다.

현재 화분 훅은 홈이 이미 받은 스탯을 초기 상태로 쓰지 않고 별도 상태 API를 호출한다. 검증된 홈 스냅샷으로 초기화하고, 복구가 필요한 경우에만 서버의 검증·복구 절차를 실행하는 방향으로 중복을 줄인다.

인증은 로그인 성공 처리에서 목적지·연결 자녀·필요한 쿠키 설정을 함께 끝내 중간 API 왕복을 줄인다. 자동 로그인도 같은 원칙을 적용한다. 서버 API의 권한 검증을 없애거나, 브라우저가 기억한 사용자 ID만 믿고 데이터를 내보내지는 않는다. 기존 P2 인증 요청 순서 보호는 유지한다.

## 2. 즉시 반응과 금액 계산 순서를 함께 보장한다

현재 미션은 자체 요청 큐, 저금통은 별도 요청 큐를 쓴다. `pendingStatsWritesRef`는 주로 오래된 스탯 응답이 화면을 덮는 것을 막는다. 이 값만으로 마켓 구매까지 같은 순서로 대기시키지는 않는다. 저금통의 처리 안내도 3초 후 표시되며 주로 저금통 버튼에 적용된다.

새 대기 기능을 여러 곳에 추가하기보다 기존 처리를 연결해, 같은 자녀의 금액·하트에 의존하는 작업 순서를 입력 순간부터 관리한다.

1. 카드 반응·소리·보상 효과는 즉시 실행한다. 저장 중인 보상은 확정 잔액과 구별할 수 있게 표시한다.
2. 사용자가 누른 순서대로 미션 지급·저금통 이동·구매 등 의존하는 계산을 예약한다. 서버 응답을 받은 확정 결과를 다음 계산의 기준으로 쓴다.
3. 패널을 여는 것과 목록을 읽는 것은 허용한다. 금액을 바꾸는 다음 행동은 대기시키거나 버튼에 처리 중 상태를 표시한다. 이전 작업이 실패하면 뒤의 작업을 무조건 실행하지 않고 실제 잔액으로 재검증한다.
4. 저금통 연속 입력 묶음은 보존할 수 있다. 다만 현재 350ms 묶음 대기 중에도 순서를 먼저 확보해야 한다. 그 사이 구매가 앞질러서는 안 되며, 다른 종류의 거래가 들어오면 앞선 묶음을 먼저 확정한다.
5. 완료 응답의 변경분·버전을 일관되게 반영하고, 오래된 조회나 실시간 이벤트의 전체 잔액으로 최신 계산을 덮지 않는다. 실패한 표시 변경도 그 작업의 범위만 취소한다.

예: 크레딧 100, 저금통 0에서 미션 +20 → 저금통에 50 이동 → 30 구매 순서라면, 확정 결과는 크레딧 40·저금통 50이다. 미션이 실패하면 +20을 사용할 수 없고 실제 잔액으로 뒤 작업을 판단해야 한다. 저금통이 실패했을 때도 성공한 것처럼 다음 계산을 이어가면 안 된다.

브라우저 순서만으로는 여러 탭·기기나 응답 유실을 해결할 수 없다. P1 계획의 DB 원자 처리·중복 요청 식별·완료 취소/재완료 구분·권한 제한이 함께 필요하다. 기존 보상 배수, 날짜, EQ, 저금통 비교 후 갱신 및 변경분 반영 이력을 보존한다. 잔액을 추측해서 절대값으로 다시 쓰는 우회는 제거 대상이다.

즉시 효과 자체도 확인한다. 현재 색종이 코드는 첫 클릭에 동적 import를 하고 소리도 클릭 시 Audio를 만든다. 서버 응답을 기다리지 않는 코드여도 첫 다운로드·디코딩 때문에 늦을 수 있다. 홈 핵심 표시 뒤 필요한 효과만 미리 준비하는 방안을 기기에서 검증한다. iOS 소리 재생의 사용자 제스처 조건은 보존한다.

## 3. “미션 생성/복구”의 정확한 의미와 자정 처리

사용자가 설정한 미션이 없다는 뜻이 아니다. 현재 데이터에는 서로 다른 두 가지가 있다.

- 미션 설정: “이 자녀는 평일에 양치하기, 보상은 얼마” 같은 반복 규칙.
- 날짜별 실행 기록: “10월 25일 양치하기는 아직 미완료” 같은 그날의 카드와 완료 여부.

자정에는 어제 기록을 지우거나 저금통·화분을 초기화하는 것이 아니라, 새 날짜의 설정에 맞는 미완료 카드가 필요하다. 현재 홈은 해당 날짜 기록이 없으면 설정에서 계산해 채운 뒤 다시 조회한다. 이때의 추가 저장·재조회가 ‘생성/복구’였다. 매 접속마다 모든 카드를 새로 만든다는 뜻은 아니다.

운영 확인 시 pg_cron은 설치되어 있지 않고 배포된 Supabase Edge Function 목록도 비어 있었다. 외부 예약 실행의 존재는 확인하지 못했으므로 자정 사전 준비가 운영 중이라고 단정할 수 없다. 저장소의 `generate-daily-missions` 함수는 현행 자녀 연결·반복 규칙과 다른 오래된 선택 로직이므로 그대로 배포하면 안 된다.

개선 순서:

1. 실제 자정 실행 경로부터 확인한다. 첫 접속, 자정 이후 계속 열린 화면, 설정 변경 직후를 따로 재현한다.
2. 홈·당일 미션 API·예약 실행이 동일한 날짜/루틴 선택 규칙을 사용하게 한다. 한국 날짜, 평일·주말, 스페셜, 개별 날짜 설정을 함께 적용한다.
3. 한국 시간 자정 예약 실행은 자녀별 당일 미션 카드 준비에만 적용한다. 다른 아이콘의 조회·계산·상태 갱신은 포함하지 않는다. 이후 설정 변경도 반영해야 하며, 이미 완료한 당일 기록과 이력은 초기화하지 않는다. 자정에 화면이 열려 있으면 새 날짜의 미션 카드만 다시 읽는다.
4. 예약 실패·신규 자녀·늦은 설정 변경을 위한 접속 시 보충 경로는 유지하되, 날짜·자녀·설정 기준으로 중복 없이 수행한다. 정상적인 미션 없는 날과 준비 실패를 구분한다.

저장 완료되지 않은 전날 작업은 요청 당시의 날짜와 작업 식별자로 마무리한다. 자정이 지났다고 새 날짜 보상으로 옮겨 지급하거나 중복 지급하지 않는다.

## 4. 화분 성장과 축하 팝업의 불일치 — 추가 신고 분석

2026-10-26 추가 신고: 성장에 필요한 하트를 모두 채웠는데 화분 크기만 바뀌고 레벨업 팝업이 나타나지 않은 사례가 있었다. 아래는 현재 코드에서 확인한 가능한 경로이며, 신고 당시의 요청 추적이나 기기 재현으로 원인을 확정한 것은 아니다.

### 확인한 구조

- `usePlantPot.water()`는 클릭 즉시 하트를 차감하고 화분 단계를 낙관적으로 올린다. 중간 단계는 즉시 `grew` 결과를 반환하지만, 마지막 7단계는 수확 결과를 받기 위해 서버 응답을 기다린다.
- `WateringCanButton`이 `water()` 반환값의 `grew`를 받으면 `ChildScreen.handlePlantGrowthCelebrate`를 호출해 팝업을 연다.
- 반면 `refresh()`와 `applyChildStatsRow()`는 저장된 화분 상태만 반영한다. 단계가 올라간 것을 발견해도 축하 결과를 전달하지 않는다. `PlantPot`의 단계 변화 감지도 반짝임 효과만 실행한다.
- 따라서 그림 갱신과 팝업 표시가 같은 성장 결과를 기준으로 보장되지 않는다. 정상 조회마다 팝업을 여는 것도 답은 아니다. 이전에 확인한 성장이나 재접속 상태까지 반복 축하할 수 있기 때문이다.

### 팝업 누락/불일치가 가능한 경로

1. **최종 성장 저장 후 응답 유실:** 서버는 7단계를 저장했지만 응답이 끊기거나 불완전하면 훅은 `ok`로 끝내고 상태를 재조회한다. 그림은 7단계로 맞춰지지만 `grew`가 전달되지 않아 축하 팝업은 열리지 않는다. 응답을 정상 수신하기 전에도 낙관적 그림은 먼저 커지므로 일시적인 어긋남 역시 존재한다.
2. **중간 단계의 예상과 서버 결과 차이:** 로컬이 성장 경계라고 판단하면 즉시 결과를 반환한다. 이후 큐의 서버 결과는 그 호출자에게 다시 전달되지 않는다. 반대로 로컬은 일반 물주기로 판단했지만 서버가 성장했다면 서버 결과로 팝업이 열린다. 빠른 연속 입력·미션 하트 지급·다른 기기 변경 시 이 기준 차이와 늦은 결과의 중복/순서 문제를 검증해야 한다.
3. **재조회·실시간 알림만으로 확인된 성장:** 그림은 갱신되지만 해당 물주기 결과를 받지 못한 경우에는 팝업이 자동 복구되지 않는다. 화면 재접속 시에도 미확인 성장 팝업을 복구할 저장 정보가 없다.
4. **성장 저장과 수확 지급의 분리:** 물주기 API는 스탯 UPDATE 후 수확 인벤토리를 별도로 갱신한다. 인벤토리 저장 실패는 `null`로 반환되어 성장만 성공할 수 있다. 이는 팝업 누락과 별개로 최종 수확 결과의 일관성도 함께 점검할 이유다.

과거 `f04ff33`의 연속 클릭 경계 잠금, `a975f26`의 화분 잠금 보완, `a69a3b5`의 수확 축하 전에 씨앗 선택 창이 나타나는 순서 수정 이력이 있다. 이 보호를 제거하거나 단순히 모든 단계 변경에 팝업을 붙이면 기존 오류가 재발할 수 있다.

### 개선안에 추가할 내용

- 물주기·하트 차감·성장 및 최종 수확 결과를 같은 작업 식별자로 확정한다. 같은 요청을 재확인해도 하트를 다시 차감하거나 수확을 중복 지급하지 않아야 한다.
- 물이 날아가는 클릭 효과는 즉시 유지하되, 확정된 성장 결과를 화분 단계와 축하 팝업의 공통 기준으로 사용한다. 중간 성장의 즉시 예고를 유지한다면 서버 확정 전 상태임을 구분하고 실패 시 정정하는 규칙이 필요하다.
- 요청 중 응답이 유실돼도 해당 작업의 성공 여부와 미확인 성장 결과를 복구할 수 있게 한다. 일반 상태 조회에서 단계 차이만 보고 임의로 새 성장 이벤트를 만들지 않는다.
- 축하는 확인 전까지 누락되지 않고 한 성장당 한 번 표시되도록 한다. 재접속까지 복구할 필요가 있다면 미확인 여부도 서버에 보관해야 한다. 단순 새로고침에 이전의 모든 성장을 다시 축하하지 않는다.
- 확정 결과 → 성장 축하 → 사용자 확인 → 다음 물주기/씨앗 선택 순서를 보장한다. 처리 중 상태와 축하창 표시 중 상태는 별도로 관리해 팝업을 닫았다고 미완료 서버 작업까지 끝난 것으로 보지 않는다.
- 하트는 미션 지급과 물주기에서 함께 사용하므로 앞서 제안한 계산 순서 및 서버 원자 처리 범위에 포함한다. 기존 최대값 선택만으로 중복 소비를 방지할 수는 없다.

검증에는 각 단계 마지막 하트 한 번/연타, 7단계 수확, 느린 응답, 저장 직후 응답 유실, 서버 실패, 미션 하트 지급 직후 물주기, 팝업 닫기 직후 재입력, 재접속·여러 탭을 포함한다. 저장 단계·하트 차감·수확 수량·팝업 횟수와 순서가 일치해야 한다.

개선·검증 순서:

1. 실제 기기에서 터치 시작 → click 진입 → 하트 상태 예약 → DOM 반영/첫 표시 구간과 물주기 응답 구간을 따로 기록한다. 일반 탭·연타·성장 경계, 첫 사용·반복 사용을 비교한다. 현재 코드만으로 지연 시간을 수치화하거나 주원인을 확정하지 않는다.

5. 입력을 터치 시작 시점으로 옮길 필요가 실제 측정에서 확인되면 드래그 취소, 스크롤, 키보드, click 중복 호출을 함께 처리한다. 단순히 onPointerDown과 onClick에 같은 함수를 붙이면 중복 물주기가 생길 수 있다.

낮은 우선순위: 전체 에셋 최적화, 일괄 인덱스 추가, 서버 지역 변경, 광범위한 리팩터링. 실제 병목으로 확인될 때만 수행한다. 위시리스트는 고립 상태를 유지하고 기능 개선 대상에서 제외한다.

검증은 첫/반복 접속, 부모의 자녀 바로가기, 자정 전후, 주말·개별 루틴, 미션 연타→저금통 연타→즉시 구매, 실패/응답 유실 후 재시도, 여러 탭, 물주기와 하트 지급의 교차를 포함한다. 최종 잔액과 완료/보상 기록이 맞고, 미저장 금액을 중복 사용하지 않아야 한다. 성공 응답 뒤 인위적인 추가 대기가 없어야 한다.

실제 기기의 인증된 전체 진입 추적과 외부 자정 스케줄은 아직 확인하지 못했다. 따라서 단축 시간을 수치로 약속하지 않으며 코드·DB 수정은 이 문서에 포함하지 않는다.
