배울 점
1. 화면(클라이언트)에서 막은 수정은 계속 재발했다. 3개월 만에 **서버 DB 트랜잭션으로 진실을 옮기고** 나서야 끝났다. 리팩토링에서 이 방향을 거꾸로 돌리면 안 된다.
2. 같은 증상이라도 원인이 달랐다. 이미 해결된 원인을 다시 고치려 하지 말고 증상이 나오면 기록(`mission_logs` 등)부터 본다.
3. 되돌려진 시도(앱 시계로 Realtime 필터링, DB 미션 템플릿 dedup 철회)는 같은 길을 다시 가지 않는다.

## 3. 리팩토링에서 절대 건드리면 안 되는 것 (회귀 방지 목록)

문서(`reward-processing-audit` 등)에 이미 근거와 함께 적힌 것을 모았다.

- 보상은 `apply_daily_mission_action`(원자적 RPC)과 `FOR UPDATE` 행 잠금, 상대 증가. 절대값 폴백을 복원하지 않는다.
- 구매·저금통의 CAS. 미션 보상이 저금통 잔액을 다시 쓰지 않는다.
- 자녀별 작업 순서 큐(`childActionQueue`)와 요청 ID 재전송. 부모 취소 시 완료 시각 검증.
- 저장 순서는 DB 시계(`updated_at` BEFORE UPDATE 트리거). 앱 시간으로 순서를 판단하지 않는다.
- 옛 `mission_completed_trigger`, mission_logs 기반 EQ 재계산 트리거는 운영 DB에서 제거됨. 다시 켜지 않는다.
- `/api/mission/complete`(삭제됨)를 복원하지 않는다. 완료 API는 `/api/daily-mission/complete` 하나.
- `last_hearts_full_date`는 text(`YYYY-MM-DD`). 날짜 타입 혼용 금지.
- 화분 성장 확인 기록(축하 복구), 화분 잠금 해제 경로.
- 보안: `20261027075623_protect_reward_writes.sql`(직접 쓰기 차단), 공개 키 검사(`public-supabase-key.test.mjs`), 관리자 키를 `NEXT_PUBLIC_*`에 넣지 않는 것.
- 로그인: 인증 요청 순서 보호(P2), 오류와 세션 없음을 구분(`/user` 500 재시도).
- 이미 있는 단위 테스트 11건(10/26 기준)은 리팩토링 전후 반드시 통과.

## 4. 코드가 이렇게 된 이유

1. **수정을 제자리에서 덧붙였다.** `ChildScreen.tsx`는 수정 커밋이 85번 닿았고, 5월 2,826줄에서 3,498줄로 계속 커졌다(+24%). 고칠 때마다 기존 자리에 가드를 추가했다.
2. **UI를 갈아엎고 부품을 안 지웠다.** 이력상 `src/` 파일 42개가 삭제됐지만(`MissionTab`, 자녀 `HomeTab`, `ChildHomeIslandStage`, `GrowthMapSheet` 등) 교체되면서 남은 부품이 21개 고아 파일이 됐다.
3. **같은 데이터를 화면마다 따로 가져온다.** 낙관적 업데이트, Realtime, `/home` 재조회, 서버 트리거 4곳이 같은 값을 만지는 구조가 크레딧 버그의 근본 원인이었다.
4. **캘린더/루틴은 모델이 중간에 바뀌었다.** 07-28 하루에 `calendar_schedule_model`, `checklists_independent`, `daily_routine_overrides` 마이그레이션이 연달아 들어갔고, 8-01에 분류 6종·루틴 2종으로 단순화됐다. 수정성 커밋 38개가 이 영역이다. 문서에는 이 모델이 없다.
5. **마이그레이션 번호 충돌**은 08-27에 한 번 정리했지만 10쌍이 남아 있다.
