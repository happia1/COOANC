## 현재 완료 처리의 실제 순서

1. 사용자/자녀 연결 확인 후 daily_missions, profiles, child_stats를 읽는다.
2. daily_missions가 미완료인지 확인하고, 미션 템플릿의 배수를 반영해 보상을 계산한다.
3. daily_missions를 완료로 저장한다. 이 UPDATE에는 `is_completed=false` 조건이나 반환 행 수 검사가 없다.
4. mission_logs를 INSERT 또는 UPDATE한다. 이 저장은 3번 및 지급 RPC와 다른 트랜잭션이다.
5. 오늘 완료율을 조회해 배 이동 여부를 계산한다.
6. complete_mission_reward가 child_stats를 잠그고 보상·경험치·스트릭·배 이동을 적용하고 EQ를 계산한다.
7. RPC 실패 시 잔액을 재조회해 지급 여부를 추측한다. `applied`가 없으면 옛 절대값 저장 경로로 내려간다.
8. 게임 이벤트와 일일 칭찬 스티커를 처리한다. 이들 역시 별도 저장이다.
9. 클라이언트는 응답/실시간 알림으로 상태를 맞춘다. 같은 탭의 완료 요청은 큐에서 순서대로 보낸다.

**6번 내부의 잔액 증가는 원자적이지만, 3~6번 전체가 원자적인 것은 아니다.** 현재 함수는 어느 dailyMissionId의 보상인지 전달받지 않아 같은 완료 시도를 알아볼 수 없다.

## 남아 있는 문제와 재현 조건

### A. 잔액 재조회로 지급 여부를 판단할 수 없음

- 미션 전 100, 미션 보상 10이 실제 반영돼 110이 된 후 응답만 끊긴다.
- 사이에 구매 20이 반영되면 재조회는 90이다. `90 >= 100+10`이 거짓이라 미지급으로 오판한다.
- `if (!applied)` 폴백은 예전 100+10을 저장해 구매 차감을 없앤다.
- 반대 사례도 있다. 실패한 미션 A의 보상은 미지급인데 미션 B의 같은 금액 보상이 들어오면, 재조회 금액만 보고 A도 지급됐다고 잘못 확정할 수 있다.

단순히 조건을 `rpcFunctionMissing && !applied`로 좁히는 것만으로 전체가 해결되지는 않는다. 그 경우 이미 완료로 저장된 카드/로그에 보상이 누락된 상태가 남을 수 있다. 현재 조각별 저장 구조를 먼저 함께 정리해야 한다.

### B. 완료 기록과 보상 저장 사이에서 실패하면 재시도할 수 없음

3번은 성공하고 4번 또는 6번이 실패하면 다음 요청은 처음의 `dm.is_completed` 검사에서 409가 된다. 카드 완료 여부는 지급 영수증이 아니다. “성공은 했는데 응답만 끊김”과 “지급 전 실패”가 지금 구조에서는 같은 모습으로 보일 수 있다.

### C. 같은 미션의 동시 재완료는 두 번 지급될 수 있음

부모 되돌리기 또는 undo-burst 뒤에는 같은 mission_logs 행이 남아 있다. 두 탭이 미완료를 동시에 읽으면 둘 다 daily_missions UPDATE, 같은 기존 로그 UPDATE, 보상 RPC를 실행할 수 있다. child_stats 행 잠금은 두 증가를 순서대로 실행할 뿐 같은 미션의 중복 지급을 막지 않는다. 기존 로그의 UNIQUE 제약도 UPDATE 두 건은 막지 않는다.

### D. RPC 권한만 막으면 보상 데이터 보호가 끝나지 않음

운영 DB에서 다음을 확인했다.

- complete_mission_reward: postgres 소유 SECURITY DEFINER, anon/authenticated 모두 EXECUTE 가능, 함수 내부 auth.uid 검사 없음. 보상값과 자녀 ID를 호출자가 전달한다.
- child_stats와 mission_logs: authenticated에 INSERT/UPDATE 권한이 있고, 본인 또는 연결 부모에게 ALL을 허용하는 RLS가 있다. 따라서 RPC를 막아도 본인 잔액/로그의 직접 조작 경로는 남는다.
- daily_missions에도 본인/부모 쓰기 정책이 있다. 특히 `parent_insert_child_daily_missions`의 조건에 `fl.child_id = fl.child_id` 자기 비교가 있어 자녀 연결을 정확히 검증하지 않는다. 이는 이번 변경에서 새로 생긴 문제가 아니다.

현재 API들이 사용자 권한의 Supabase 클라이언트로 쓰기 작업을 하므로, authenticated의 UPDATE를 즉시 전부 차단하면 정당한 미션·구매·물주기·되돌리기도 멈춘다. 클라이언트의 알람 설정, 온보딩, 화분 초기화/복구에서도 child_stats를 직접 갱신한다. **서버 전용 지급 경로로의 이관과 컬럼별 권한 분리를 함께 설계해야 한다.**

## 수정 설계: 반드시 보존할 동작

- 미션의 배수 보상, XP/레벨 공식, 배정일 기준 스트릭, 90% 항해 판정과 하루 1회 게이트.
- 부모 되돌리기 및 “미안, 다시 할게” 후 정당한 재완료. 같은 dailyMissionId를 영구히 한 번만 지급하게 만들면 기능이 깨진다.
- 미션 지급 시 저금통을 건드리지 않는 부분 업데이트, 구매/저금통/씨앗/되돌리기의 CAS 또는 동등한 DB 행 잠금.
- 보상 반영 후 EQ 계산, DB 시계 통일, 화면의 저금통 delta 반영 및 실시간 동기화.
- 일일 스티커/꾸미기 이벤트는 미션 금전 보상과 별개의 1회 조건이다. 해당 중복 방지 키를 보상 지급 영수증으로 재사용하지 않는다.

## 제안하는 정리 순서 — 아직 적용하지 않음

1. **완료·지급·되돌리기의 재시도 기준을 먼저 결정한다.** 일일 미션 ID와 완료 시도의 버전/토큰을 식별자로 사용한다. 현재 행 잠금과 미완료→완료 전환, 로그 저장, 보상 증가를 한 DB 트랜잭션으로 묶는다. 이미 처리된 같은 시도는 추가 지급 없이 현재 결과를 반환한다. 단순한 “지급 테이블 하나 추가”만으로 해결되지 않는다.
2. **되돌리기도 같은 경계에 맞춘다.** 완료 상태/로그/정확한 지급액 차감을 한 번만 적용하고 다음 완료 버전으로 넘긴다. 이전 버전의 늦은 완료 재시도는 거절하고, 새 버전의 정상 재완료는 허용한다. 잠금 순서는 완료/취소 양쪽에서 동일하게 유지한다.
3. **공개 호출과 내부 지급을 분리한다.** 새 내부 지급 함수는 service_role만 실행하게 하고, API는 사용자·가족 연결·시간 제약·배수 보상을 검증한다. 직접 수정 가능한 보호 컬럼(credits/hearts/XP/지급 로그 등)을 정리하고 정상 쓰기 호출자를 이관한 뒤 일반 사용자 쓰기 권한을 줄인다. 알람 등 허용해야 하는 설정 컬럼은 따로 남긴다.
4. **검증한 지급 결과만 응답한다.** 기존 잔액 추측과 절대값 폴백을 제거한다. 미적용 환경은 명확히 실패하게 하되 완료 표시만 저장되지 않도록 1번과 같이 배포한다. 42883은 함수 없음과 내부 연산자/함수 오류를 구분한다.
5. **DB 정합성 다음에 화면 가드를 정리한다.** 기존 여러 시각/누적값 가드를 근거 없이 삭제하지 않는다. 동일 완료의 중복·응답 유실·다른 탭의 구매·저금·되돌리기를 검증한 후 각 가드의 필요성을 따로 판단한다.

필수 검증: 최초 완료, 같은 시도 동시 요청/재시도, 응답만 유실 후 재시도, 완료 저장 중 실패, 되돌리기 중 실패, 취소 후 재완료, 이전 완료의 늦은 재시도, 보상과 구매/저금/씨앗 사용 동시 실행, 보상 배수, XP/스트릭/배 이동, 비로그인·타인·본인 임의 금액 조작 차단. 실제 사용자 잔액을 바꿔 공격 재현하지 않는다.

운영 DB의 기존 중복 트리거 제거와 함수 날짜 수정은 확인됐지만, 과거 모든 부분 실패의 발생 횟수 및 사용자별 손실량은 확보된 기록만으로 확정할 수 없다. 이번 작업은 이 분석과 P2 인증 요청 직렬화까지만 수행한다.
